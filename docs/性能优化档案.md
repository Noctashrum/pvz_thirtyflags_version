# 性能优化档案（每轮留档）

> 本文档专门记录**原版引擎的性能瓶颈定位与优化手段**，每轮追加一节。
> 原则：**只写有实测支撑的结论**；拿不出收益的改动也如实记录（含"被数据否掉"的方向），
> 避免后人重复调查。
>
> 环境基准：PvZ 逻辑**每帧跑一次**，帧率上限 **100fps → 帧预算 10ms**。
> 因此"帧时间 > 10ms"不只是掉帧，而是**整个游戏变慢**。

---

## 总账（截至第 2 轮）

| # | 优化项 | 位置 | 手法（算法 / 数据结构） | 实测收益 | 提交 |
|---|---|---|---|---|---|
| 1 | 对象池遍历 | `TodLib/DataArray.h` `IterateNext` | 活槽位位图 + 32 槽整段跳空 + `_BitScanForward` | **微基准实测反而慢 0.6x**（见 §1，诚实记录） | `0b1ad38` |
| 2 | 精灵合批 | `D3DInterface.cpp` `TextureData::Blt` | 按 (纹理, 混合模式) 聚合成三角列表，一次提交 | **绘制调用 684 → 599（−12%）** | `e56ce77` |
| 3 | 绘制状态去重 | `D3DInterface.cpp` `SetupDrawMode` | 缓存当前混合模式，只在变化时下发 | 每个精灵省 2 次 `SetRenderState` | `e56ce77` |
| 4 | 火豌豆骨骼动画去重 | `Projectile.cpp` `ConvertToFireball` | 已是火球则跳过重复表现创建（状态照旧叠加） | 叠种 N 层树桩：N 条骨骼动画 → **1 条** | `0b1ad38` |
| 5 | 裸土条带合并 | `ThirtyFlags.cpp` `DrawBackdrop` | 连续未开放行的条带合并为一次 blit | 锁 4 行时 4 次 → **2 次** | `0b1ad38` |
| 6 | 投射物碰撞按行分桶 | `Board.cpp` + `Projectile.cpp` | 按行分桶（uniform bucket by lane） | `O(P×Z) → O(P×Z/行数)`（该循环量级 ↓ ~5x） | `c96d4e6` |
| 7 | **构建链修复**（非运行时） | `tools/build_manual.py` | 框架 unity 目标依赖检查 | 让 #2/#3 **真正生效**（见 §7） | `e56ce77` |

**一句话总结**：原版真正的瓶颈是**渲染的绘制调用数**（draw-call bound），
纯代码层面能拿到的确定收益是「**去重**」与「**分桶**」；
**数量级的提升需要资产图集化**（属美术管线，不在纯代码范围）。

## §0 定位手段与工具（先有测量，再谈优化）

| 工具 | 作用 |
|---|---|
| `[TFPerf]` 每帧探针 | 把一帧拆成 **update / draw / idle** 三段 + 实体规模 + `sprite=四边形数/调用数`，每 500 帧写一行到 `Release/thirtyflags_flow.log` |
| `tools/tf_perf_bench.ps1` | **自动造重载场景**：进局后用作弊键 `q` 瞬间铺满「机枪+火炬+南瓜+睡莲」 |
| `tools/tf_perf_ab.ps1` | A/B 对照（带 `-Tag` 参数） |
| `tools/flip_batch.py` | 一键切换精灵合批开关（`TF_SPRITE_BATCH`） |

**关键实测数据（这是后面所有判断的依据）**：

| 场景 | update | **draw** | idle | sprite |
|---|---|---|---|---|
| 空场 | 0.1ms | **0.3ms** | 9.6ms | — |
| 31 僵尸 | 0.2ms | **3.1~5.4ms** | 5~7ms | — |
| 57 僵尸 | 0.0~0.1ms | **7.0~8.0ms** | 3~8ms | 363/265 |

两条结论：
1. **update 侧恒定 0.0~0.3ms** → 更新逻辑（含各种 `O(n²)` 目标搜索）在 2000 年代硬件上才吃紧，现代 CPU 上不是瓶颈；
2. **draw 随精灵数线性膨胀**，`sprite` 计数与 draw 时间对得上 → **每次绘制调用约 5~6µs**
   （D3D7 即时模式在现代 Windows 上的兼容层开销）。

## §1 对象池遍历：活槽位图（**被数据否掉的一次优化**）

* **问题假设**：`DataArray<T>::IterateNext` 从当前槽**逐槽线性扫到 `mMaxUsedCount`**，
  而槽里是几百字节的大对象（Zombie/Plant/Projectile）→ 每次遍历都在探测空槽，必然 cache miss。
* **手段**：活槽位位图（一位一槽）+ 整段 32 槽跳空（本质就是**分块**），
  `_BitScanForward` 定位最低置位，空池 O(1) 快路径；读档后按 `mID` 重建位图。
* **等价性验证**：随机化测试 572 次比对，遍历**长度与顺序完全一致**（含读档重建、FreeAll、满池、溢出）。
* **实测（1024 槽池单次完整遍历，500 次平均）**：

  | 场景 | 线性扫描（原实现） | 位图+逐位 | 位图+BSF |
  |---|---|---|---|
  | 245 活 / 64B 槽 | **1.51µs** | 5.62µs | 2.52µs |
  | 245 活 / 4096B 槽 | **2.20µs** | — | 2.59µs |
  | 950 活 / 2048B 槽 | **1.07µs** | 11.66µs | 5.21µs |

* **结论（重要）**：**顺序扫描已贴着内存带宽跑，换"更聪明"的结构反而慢 1.7~3.7 倍。**
  规模只有 10³ 且访问顺序时，**渐进复杂度已无空间**，决定性能的是访存模式/分支/每项工作量。
* **保留理由**：把最坏情况（大量空槽）从 O(容量) 压到 O(容量/32)，且等价性有测试保证；
  但它**不是**卡顿的解药 —— 记录在此以免后人再走一遍。

## §2 精灵合批：按 (纹理, 混合模式) 聚合成三角列表

* **定位**：`TextureData::Blt` 对**每个四边形**发 `SetTexture` + `DrawPrimitive(4 顶点即时模式)`；
  一帧上千精灵 = 上千次绘制调用 → **draw-call bound**（GPU 挨饿）。
* **手段**：连续「同纹理 + 同混合模式」的四边形攒进三角列表（6 顶点/四边形），一次提交；
  顶点数据、四边形先后顺序**一律不变**。
* **正确性纪律**（缺一不可）：
  * 混合模式变化（`SetupDrawMode`）、纹理滤镜变化（`SetLinearFilter`）、
    视口变化（`UpdateViewport`）、任何其它绘制入口、帧末（`Flush`）→ **强制 flush**；
    （批次顶点是**提交时**才取状态，所以状态一变必须先提交，否则会吃到新状态）
  * 由 CPU 多边形裁剪的四边形与批次**互斥**（进入前先 flush）。
* **实测收益**：`sprite=684/599` → **调用数 −12%**。
* **为什么只有 12%**：**这套美术没有图集（atlas）**，每个图像是独立纹理，
  相邻精灵几乎不可能同纹理 → 按纹理合批天然受限。
  → 想要数量级收益必须**资产图集化**（美术管线，不在纯代码范围）。
* **附带**：`DrawBackdrop` 的连续未开放行条带合并为一次 blit（像素一致）。

## §3 绘制状态去重

* `SetupDrawMode` 原来**每个精灵**无条件发 2 次 `SetRenderState`（SRCBLEND/DESTBLEND）。
* 改为缓存当前混合模式，只在**真正变化**时下发；模式变化时先 flush 批次。
* 收益：每个精灵省 2 次状态调用（未单独量化，但作用于全部精灵）。
* 同时确认：`SetLinearFilter` **原本就有缓存**（只在变化时下发 3 条纹理状态）→ 无优化空间。

---

## §4 重复表现去重：火豌豆骨骼动画

* **定位**：叠种火炬时，同格 N 个树桩会让同一颗豌豆走 N 次转换，
  而原实现**每次调用都新建一条 `REANIM_FIRE_PEA` 骨骼动画**并挂到这颗弹上
  → 同一颗弹养 N 条骨骼动画；再乘上多格火炬、机枪 4 发/轮、多株叠种 = 物品创建暴涨。
* **手段**：**状态照旧逐层叠加**（伤害/元素完全不变），只在「已经是火球」时跳过重复的表现创建。
* 视觉零差异（多层火焰本来就重合在同一个位置），但**骨骼动画的更新+绘制直接少 N−1 份**。

---

## §5 裸土条带合并

* `DrawBackdrop` 原来每个未开放的行各画一次 `IMAGE_BACKGROUND1UNSODDED` 条带（720×100）。
* 贴图与场地纵向布局一致（原实现就是"源 y = 目标 y"）→ **相邻锁着行合并成一个更高的源矩形**，
  画出来的像素与逐行画完全一致，绘制调用更少（5 行锁 4 行时：4 次 → 2 次）。

---

## §6 投射物碰撞按行分桶

* **定位**：`Projectile::FindCollisionTarget` 对**每个投射物**遍历**整个僵尸池**，
  只有一次 `mRow` 过滤 → `245 投射物 × 49 僵尸 ≈ 1.2 万次/帧`，且随两者**乘积**增长。
* **手段**：僵尸本来就按行活动（5~6 行）→ **按行分桶**（lane bucket），
  `O(P×Z) → O(P×Z/行数)`。
* **为什么可以安全替换**：该函数取「**最左侧**重叠目标」（`aZombie->mX < aMinX`），
  **与遍历顺序无关**；BOSS 不分行（任何行都能打），单独遍历。
  （对照：`Plant::FindTargetZombie` / `Zombie::FindZombieTarget` 是"权重最高"选目标，
  **权重并列时由遍历顺序决定** → **不能**换结构，否则会偷改游戏行为。）
* **实现要点**：`Board::GetRowZombieCount/GetRowZombie/GetBossZombie*/GetBossZombieByIndex`；
  **文件级静态桶**（不动 `Board` 成员 → 存档兼容，`SyncBoard` 按 `sizeof(Board)` 整块写盘）；
  桶在「僵尸池 `mSize` 变化」或「跨帧（`mMainCounter` 变化）」时**惰性重建**；
  每行容量 `TF_ROW_BUCKET_MAX = 256`（6×256×4B ≈ 6KB，常驻缓存）。

> **通用判据**：只有「**结果与遍历顺序无关**」的循环才允许换索引结构。

## §7 构建链修复：框架 unity 目标不重编（**让渲染优化能生效的前提**）

* **现象/风险**：`SexyAppFramework` 是**预编译 unity 构建** —— `GraphicsBuild.cpp` 里
  `#include "D3DInterface.cpp" / "Graphics.cpp" / "DDImage.cpp" …`，
  而**这套源文件不在 `Lawn.vcxproj` 里**（vcxproj 只引用一处 SexyAppFramework 的 include 路径）。
  → **改渲染器源码不会重编，链接进去的还是旧实现：改了等于没改，且没有任何报错。**
* **手段**：`tools/build_manual.py` 增加「框架 unity 依赖检查」：
  unity obj 比 unity cpp 旧、或比任一被 `#include` 的 cpp 旧、或比任一框架头新 → 重编该 unity
  （覆盖 `GraphicsBuild / MiscBuildBase / SoundBuild / WidgetBuildBase / SexyAppBase / SexyApp`）。
* 这一条**本身不提升运行时性能**，但它是 §2/§3 能落地的前提。

## §8 已排除项（看着像瓶颈，实际没有空间 / 不能动）

| 位置 | 结论 | 原因 |
|---|---|---|
| `Graphics::DrawImage` 离屏剔除 | **已经有了** | 内部已 `Intersection(mClipRect)`，空矩形直接跳过 |
| 每帧堆分配（`std::string`/`vector`/`new`） | **干净** | 绘制/更新热路径无 per-frame 分配 |
| `D3DInterface::CheckDXError` | 便宜 | 成功路径只是一次 HRESULT 比较 |
| `SetLinearFilter` | 已缓存 | 只在真正变化时下发 |
| 渲染列表排序 | 已最优 | `std::sort` + 整数比较（`mRenderOrder`） |
| `Plant::FindTargetZombie` / `Zombie::FindZombieTarget` | **不能动** | 权重并列时由遍历顺序决定选中目标 |
| 把逻辑搬去 GPU | 无意义 | 像素**本来就在 GPU 上**，瓶颈是 CPU 侧调用数（draw-call bound） |
| 线段树 / 树状数组 | **不适用** | 它们是**区间查询**结构；这里的查询是"同行的最近目标"（空间查询）→ 正解是分桶/网格/单轴扫描 |

## §9 一次被数据推翻的假设（记录以免重走）

**假设**：`z=57` 时 draw 7~8ms，但计数只有 363 个四边形（≈20µs/个，远高于普通路径）
→ 推断"多数精灵走的是带变换的 `TextureData::BltTransformed`，其中被 **CPU 多边形裁剪**
（`DrawPolyClipped`）的四边形不走批次、每个都要做多边形裁剪"。

**验证**：给该路径加了计数 `clip=N`（走 CPU 裁剪的四边形数）后重测：

```
[TFPerf] ... draw=4.0ms ... z=31 pl=3 pr=1 reanim=50 emit=16 part=148 | sprite=976/898 clip=0 3d=1
```

* **`clip=0`** → 没有任何四边形走 CPU 多边形裁剪 → **假设被推翻**；
* 976 个四边形 / 898 次调用 / 4.0ms → **≈4.1µs 每次绘制调用**，与早先测得的 5~6µs 同量级，
  说明"每次调用约 4~6µs"是稳定的，之前的 20µs 那个点是窗口内混入了别的负载（误读）。

**因此结论修正**：绘制成本 ≈（四边形数 × 4~6µs），且**合批只能省 ~8~12%**（没有图集）。
纯代码层面已经没有"结构性的"绘制优化空间了。

## §10 下一步（按预期收益排序，修正版）

1. **减少精灵数量（纯代码，唯一还有空间的方向）**
   离屏剔除已由引擎完成、CPU 裁剪路径实测为 0 → 只能从**源头少画**：
   * 继续做"重复表现去重"（已有：火豌豆骨骼动画；可扩展：同帧同位置的同类特效合并）；
   * 静态/低频变化的图层合并成一次 blit（如背景 + 裸土 + 水面的合成缓存），
     数量级小但零风险；
   * 检查粒子发射量是否有"必然重叠"的浪费（同格多株植物的同类粒子）。
2. **资产图集化**（唯一能把 draw 调用数降一个数量级的路子，属美术管线，不在"纯代码"范围）
3. 更新侧（update）目前恒为 0.0~0.3ms，**不是瓶颈**；只有在实体数再涨 10 倍时才需要动
   （那时的正解是 §6 那类分桶/index，而不是树状数组）。

## 附：如何复现本文档的所有数据

```bash
# 1) 构建（debug 带探针日志；player 用于实际游玩）
python tools/build_manual.py            # 调试版 → Release\PlantsVsZombies.exe
python tools/build_manual.py --player   # 游玩版 → Release\PlantsVsZombies_Play.exe

# 2) 跑基准（静默：最小化启动、不抢焦点、不动鼠标），结果写 docs/perf/
powershell -ExecutionPolicy Bypass -File tools/tf_perf_bench.ps1
powershell -ExecutionPolicy Bypass -File tools/tf_perf_ab.ps1 -Tag xxx

# 3) 看数据
#    Release\thirtyflags_flow.log 里的 [TFPerf] 行
#    sprite=四边形数/实际绘制调用数 clip=走CPU裁剪的四边形数

# 4) 切换合批开关做 A/B
python tools/flip_batch.py 0   # 关
python tools/flip_batch.py 1   # 开
```

> 基准脚本偶尔会「进不了局」（菜单时序漂移），表现为报告里没有 `[TFPerf]` 行。
> 判断是"真崩了"还是"没进局"：查 `Release/pvzdebug.log` 有没有 `UNHANDLED EXCEPTION`。
