# 性能优化档案（每轮留档）

> 本文档专门记录**原版引擎的性能瓶颈定位与优化手段**，每轮追加一节。
>   
> 原则：**只写有实测支撑的结论**；拿不出收益的改动也如实记录（含"被数据否掉"的方向），
>   
> 避免后人重复调查。
>
> 环境基准：PvZ 逻辑**每帧跑一次**，帧率上限 **100fps → 帧预算 10ms**。
>   
> 因此"帧时间 > 10ms"不只是掉帧，而是**整个游戏变慢**。

## §0 定位手段与工具（先有测量，再谈优化）

| 工具                        | 作用                                                                                                      |
| ------------------------- | ------------------------------------------------------------------------------------------------------- |
| `[TFPerf]` 每帧探针           | 把一帧拆成 **update / draw / idle** 三段 + 实体规模 + `sprite=四边形数/调用数`，每 500 帧写一行到 `Release/thirtyflags_flow.log` |
| `tools/tf_perf_bench.ps1` | **自动造重载场景**：进局后用作弊键 `q` 瞬间铺满「机枪+火炬+南瓜+睡莲」                                                               |
| `tools/tf_perf_ab.ps1`    | A/B 对照（带 `-Tag` 参数）                                                                                     |
| `tools/flip_batch.py`     | 一键切换精灵合批开关（`TF_SPRITE_BATCH`）                                                                           |

**关键实测数据（这是后面所有判断的依据）**：

| 场景    | update    | **draw**      | idle  | sprite  |
| ----- | --------- | ------------- | ----- | ------- |
| 空场    | 0.1ms     | **0.3ms**     | 9.6ms | —       |
| 31 僵尸 | 0.2ms     | **3.1~5.4ms** | 5~7ms | —       |
| 57 僵尸 | 0.0~0.1ms | **7.0~8.0ms** | 3~8ms | 363/265 |

两条结论：

1. **update 侧恒定 0.0~0.3ms** → 更新逻辑（含各种 `O(n²)` 目标搜索）在 2000 年代硬件上才吃紧，现代 CPU 上不是瓶颈；
2. **draw 随精灵数线性膨胀**，`sprite` 计数与 draw 时间对得上 → **每次绘制调用约 5~6µs**
     
   （D3D7 即时模式在现代 Windows 上的兼容层开销）。

## §1 对象池遍历：活槽位图（**被数据否掉的一次优化**）

- **问题假设**：`DataArray<T>::IterateNext` 从当前槽**逐槽线性扫到 `mMaxUsedCount`**，
    
  而槽里是几百字节的大对象（Zombie/Plant/Projectile）→ 每次遍历都在探测空槽，必然 cache miss。
- **手段**：活槽位位图（一位一槽）+ 整段 32 槽跳空（本质就是**分块**），
    
  `_BitScanForward` 定位最低置位，空池 O(1) 快路径；读档后按 `mID` 重建位图。
- **等价性验证**：随机化测试 572 次比对，遍历**长度与顺序完全一致**（含读档重建、FreeAll、满池、溢出）。
- **实测（1024 槽池单次完整遍历，500 次平均）**：
  | 场景              | 线性扫描（原实现）  | 位图+逐位   | 位图+BSF |
  | --------------- | ---------- | ------- | ------ |
  | 245 活 / 64B 槽   | **1.51µs** | 5.62µs  | 2.52µs |
  | 245 活 / 4096B 槽 | **2.20µs** | —       | 2.59µs |
  | 950 活 / 2048B 槽 | **1.07µs** | 11.66µs | 5.21µs |
- **结论（重要）**：**顺序扫描已贴着内存带宽跑，换"更聪明"的结构反而慢 1.7~3.7 倍。**
    
  规模只有 10³ 且访问顺序时，**渐进复杂度已无空间**，决定性能的是访存模式/分支/每项工作量。
- **保留理由**：把最坏情况（大量空槽）从 O(容量) 压到 O(容量/32)，且等价性有测试保证；
    
  但它**不是**卡顿的解药 —— 记录在此以免后人再走一遍。

## §2 精灵合批：按 (纹理, 混合模式) 聚合成三角列表

- **定位**：`TextureData::Blt` 对**每个四边形**发 `SetTexture` + `DrawPrimitive(4 顶点即时模式)`；
    
  一帧上千精灵 = 上千次绘制调用 → **draw-call bound**（GPU 挨饿）。
- **手段**：连续「同纹理 + 同混合模式」的四边形攒进三角列表（6 顶点/四边形），一次提交；
    
  顶点数据、四边形先后顺序**一律不变**。
- **正确性纪律**（缺一不可）：
  - 混合模式变化（`SetupDrawMode`）、纹理滤镜变化（`SetLinearFilter`）、
      
    视口变化（`UpdateViewport`）、任何其它绘制入口、帧末（`Flush`）→ **强制 flush**；
      
    （批次顶点是**提交时**才取状态，所以状态一变必须先提交，否则会吃到新状态）
  - 由 CPU 多边形裁剪的四边形与批次**互斥**（进入前先 flush）。
- **实测收益**：`sprite=684/599` → **调用数 −12%**。
- **为什么只有 12%**：**这套美术没有图集（atlas）**，每个图像是独立纹理，
    
  相邻精灵几乎不可能同纹理 → 按纹理合批天然受限。
    
  → 想要数量级收益必须**资产图集化**（美术管线，不在纯代码范围）。
- **附带**：`DrawBackdrop` 的连续未开放行条带合并为一次 blit（像素一致）。

## §3 绘制状态去重

- `SetupDrawMode` 原来**每个精灵**无条件发 2 次 `SetRenderState`（SRCBLEND/DESTBLEND）。
- 改为缓存当前混合模式，只在**真正变化**时下发；模式变化时先 flush 批次。
- 收益：每个精灵省 2 次状态调用（未单独量化，但作用于全部精灵）。
- 同时确认：`SetLinearFilter` **原本就有缓存**（只在变化时下发 3 条纹理状态）→ 无优化空间。

## §4 重复表现去重：火豌豆骨骼动画

- **定位**：叠种火炬时，同格 N 个树桩会让同一颗豌豆走 N 次转换，
    
  而原实现**每次调用都新建一条 `REANIM_FIRE_PEA` 骨骼动画**并挂到这颗弹上
    
  → 同一颗弹养 N 条骨骼动画；再乘上多格火炬、机枪 4 发/轮、多株叠种 = 物品创建暴涨。
- **手段**：**状态照旧逐层叠加**（伤害/元素完全不变），只在「已经是火球」时跳过重复的表现创建。
- 视觉零差异（多层火焰本来就重合在同一个位置），但**骨骼动画的更新+绘制直接少 N−1 份**。

## §5 裸土条带合并

- `DrawBackdrop` 原来每个未开放的行各画一次 `IMAGE_BACKGROUND1UNSODDED` 条带（720×100）。
- 贴图与场地纵向布局一致（原实现就是"源 y = 目标 y"）→ **相邻锁着行合并成一个更高的源矩形**，
    
  画出来的像素与逐行画完全一致，绘制调用更少（5 行锁 4 行时：4 次 → 2 次）。

---

## §6 投射物碰撞按行分桶

- **定位**：`Projectile::FindCollisionTarget` 对**每个投射物**遍历**整个僵尸池**，
    
  只有一次 `mRow` 过滤 → `245 投射物 × 49 僵尸 ≈ 1.2 万次/帧`，且随两者**乘积**增长。
- **手段**：僵尸本来就按行活动（5~6 行）→ **按行分桶**（lane bucket），
    
  `O(P×Z) → O(P×Z/行数)`。
- **为什么可以安全替换**：该函数取「**最左侧**重叠目标」（`aZombie->mX < aMinX`），
    
  **与遍历顺序无关**；BOSS 不分行（任何行都能打），单独遍历。
    
  （对照：`Plant::FindTargetZombie` / `Zombie::FindZombieTarget` 是"权重最高"选目标，
    
  **权重并列时由遍历顺序决定** → **不能**换结构，否则会偷改游戏行为。）
- **实现要点**：`Board::GetRowZombieCount/GetRowZombie/GetBossZombie*/GetBossZombieByIndex`；
    
  **文件级静态桶**（不动 `Board` 成员 → 存档兼容，`SyncBoard` 按 `sizeof(Board)` 整块写盘）；
    
  桶在「僵尸池 `mSize` 变化」或「跨帧（`mMainCounter` 变化）」时**惰性重建**；
    
  每行容量 `TF_ROW_BUCKET_MAX = 256`（6×256×4B ≈ 6KB，常驻缓存）。

> **通用判据**：只有「**结果与遍历顺序无关**」的循环才允许换索引结构。

## §7 构建链修复：框架 unity 目标不重编（**让渲染优化能生效的前提**）

- **现象/风险**：`SexyAppFramework` 是**预编译 unity 构建** —— `GraphicsBuild.cpp` 里
    
  `#include "D3DInterface.cpp" / "Graphics.cpp" / "DDImage.cpp" …`，
    
  而**这套源文件不在 `Lawn.vcxproj` 里**（vcxproj 只引用一处 SexyAppFramework 的 include 路径）。
    
  → **改渲染器源码不会重编，链接进去的还是旧实现：改了等于没改，且没有任何报错。**
- **手段**：`tools/build_manual.py` 增加「框架 unity 依赖检查」：
    
  unity obj 比 unity cpp 旧、或比任一被 `#include` 的 cpp 旧、或比任一框架头新 → 重编该 unity
    
  （覆盖 `GraphicsBuild / MiscBuildBase / SoundBuild / WidgetBuildBase / SexyAppBase / SexyApp`）。
- 这一条**本身不提升运行时性能**，但它是 §2/§3 能落地的前提。

## §8 已排除项（看着像瓶颈，实际没有空间 / 不能动）

| 位置                                                     | 结论       | 原因                                                 |
| ------------------------------------------------------ | -------- | -------------------------------------------------- |
| `Graphics::DrawImage` 离屏剔除                             | **已经有了** | 内部已 `Intersection(mClipRect)`，空矩形直接跳过              |
| 每帧堆分配（`std::string`/`vector`/`new`）                    | **干净**   | 绘制/更新热路径无 per-frame 分配                             |
| `D3DInterface::CheckDXError`                           | 便宜       | 成功路径只是一次 HRESULT 比较                                |
| `SetLinearFilter`                                      | 已缓存      | 只在真正变化时下发                                          |
| 渲染列表排序                                                 | 已最优      | `std::sort` + 整数比较（`mRenderOrder`）                 |
| `Plant::FindTargetZombie` / `Zombie::FindZombieTarget` | **不能动**  | 权重并列时由遍历顺序决定选中目标                                   |
| 把逻辑搬去 GPU                                              | 无意义      | 像素**本来就在 GPU 上**，瓶颈是 CPU 侧调用数（draw-call bound）     |
| 线段树 / 树状数组                                             | **不适用**  | 它们是**区间查询**结构；这里的查询是"同行的最近目标"（空间查询）→ 正解是分桶/网格/单轴扫描 |

## §9 一次被数据推翻的假设（记录以免重走）

**假设**：`z=57` 时 draw 7~8ms，但计数只有 363 个四边形（≈20µs/个，远高于普通路径）
  
→ 推断"多数精灵走的是带变换的 `TextureData::BltTransformed`，其中被 **CPU 多边形裁剪**
  
（`DrawPolyClipped`）的四边形不走批次、每个都要做多边形裁剪"。

**验证**：给该路径加了计数 `clip=N`（走 CPU 裁剪的四边形数）后重测：

```
[TFPerf] ... draw=4.0ms ... z=31 pl=3 pr=1 reanim=50 emit=16 part=148 | sprite=976/898 clip=0 3d=1
```

- **`clip=0`** → 没有任何四边形走 CPU 多边形裁剪 → **假设被推翻**；
- 976 个四边形 / 898 次调用 / 4.0ms → **≈4.1µs 每次绘制调用**，与早先测得的 5~~6µs 同量级，
    
  说明"每次调用约 4~~6µs"是稳定的，之前的 20µs 那个点是窗口内混入了别的负载（误读）。

**因此结论修正**：绘制成本 ≈（四边形数 × 4~6µs），且**合批只能省 ~~8~~12%**（没有图集）。
  
纯代码层面已经没有"结构性的"绘制优化空间了。

## §11 纹理图集（sprite atlas）：把"每次调用 4µs"这块预算整块腾出来【进行中】

### 11.1 为什么这是**数量级**的机会

上一轮已确认：绘制成本 ≈ **四边形数 × 4~6µs**，而合批只能省 8~12%，
根因是**这张美术每张图各自一个纹理**（`TextureDataPiece` 一个 piece 一个 DDraw surface），
相邻精灵几乎不可能同纹理。

实测佐证：`sprite=976/898`（976 个四边形只合并成 898 次调用）。

**若把它们装进同一张图集**：按 256 四边形/批，976 → **约 4 次提交**，
绘制调用下降约**两个数量级**；按 4µs/次估算，draw 从 4ms 降到 ~0.5ms
→ **腾出约 3.5ms/帧**（帧预算 10ms 的 35%）。这才是"能换帅特效"的那笔预算。

**关键点：不需要改美术资源。** 图集在**运行时**用装箱算法把现有散图打进共享大纹理，
再把 UV 重映射一层即可（业界标准 sprite atlas + UV remap 做法）。

### 11.2 插入点（已确认，改动有界）

`TextureData` 本来就是"图像 → 若干 piece → 每 piece 一个纹理"：

| 步骤 | 现状 | 图集版 |
|---|---|---|
| 建纹理 | `CreateTextureSurface(w, h, format)` 每 piece 一张 | 从**共享图集页**里分配子矩形 |
| 拷贝 | `CopyImageToTexture(piece表面, image, x, y, w, h, fmt)` | 同函数 + **目标偏移**（写进图集子矩形） |
| 取纹理 | `GetTexture()` 返回 piece 表面 + `u/v = 局部/片宽` | 返回**图集页** + `u/v = (图集偏移+局部)/页宽` |
| UV 缩放 | `mMaxTotalU/V = 图宽/片宽` | 图集版取 **1.0**（UV 已是绝对值） |

### 11.3 装箱算法：货架装箱（shelf packing）——**已实现并独立验证**

* 选型理由：PvZ 的散图尺寸差异极大（8×8 的小图标 ~ 420×620 的整只僵尸）。
  在线贪心的**货架装箱**每次分配只需比较一个游标，**O(1)/次**；
  相比通用 `MaxRects`，实现与常数都便宜得多，对"先到先放、不重排"的场景足够。
* 每块额外留 **1px 间隙（gutter）**，避免线性过滤采样到邻居像素。
* 失败时**整张图回退**到原来的「一 piece 一纹理」，保证任何情况都不会画错。
* **独立验证**（把函数逐字抽出来配桩测，驱动 PvZ 风格的尺寸分布）：

  ```
  placed=518  failed=0  pages=9
  overlaps=0  outOfBounds=0
  occupancy=73.2%   (页扫描面积 / 页面积)
  ```

  → 无重叠、无越界、占用率 73.2%（货架装箱在混合尺寸下的合理水平）。

### 11.4 剩余工作（分三步，每步可验证）

1. **接线**：`CreateTextures` 改走图集分配 + 目标偏移拷贝；`TextureDataPiece` 加 `mAtlasX/mAtlasY`；
   `GetTexture/GetTextureF` 返回图集 UV；图集图 `mMaxTotalU/V = 1`。
2. **A/B 验证**：用 `tools/flip_atlas.py`（待写）切换 `TF_TEXTURE_ATLAS`，
   对比 `sprite=quads/calls` 与 draw ms，并**截图逐像素核对**（必须与原来一致）。
3. 若图集生效，再考虑：把常用精灵**按绘制顺序**预排进图集（提高同批连续率）、
   以及**单顶点缓冲 + 索引**进一步减少提交次数。

### 11.5 ⚠️ 特效层的设计约束（给"帅的特效"用）

一旦有了合批，**特效的性价比排序完全变了**。设计约束：

* **同批 = 同纹理 + 同混合模式** → 特效要尽量用**同一张特效图集**，并且
  **按混合模式分批**（加色类特效集中画、普通透明度类集中画），否则一次模式切换就拆一次批；
* 最划算的特效形态是**加色四边形**（additive quad）：拖尾、光晕、冲击环、元素拖尾
  都是"每帧几个四边形"的事，合批后几乎免费；
* **不要**用"每个特效一个骨骼动画"的做法（那是上一轮 §4 里火豌豆踩过的坑：
  同一颗弹养了 N 条骨骼动画）。


## §12 纹理图集：跑通了，但**收益远小于估计**（重要更正）

### 12.1 结论先说

| 指标 | 图集前 | 图集后 |
|---|---|---|
| 一帧绘制调用数 | 898 | **831** |
| 四边形数 | 976 | 976 |
| draw 时间 | ~4.0ms | ~3.3ms |

**只降了 8%**，不是我先前估的"两个数量级"。**先把话说清楚：那个估计是错的。**

### 12.2 为什么估计错了

我的估计隐含假设是"**所有精灵会共用同一张纹理**"。实际跑起来：

```
[TFAtlas] device max tex = 1024x1024, formats=0x7 -> page size = 1024
[TFAtlas] page 0 created: 1024 x 1024 fmt=4
[TFAtlas] page 1 created: 1024 x 1024 fmt=1
[TFAtlas] page 2 created: 1024 x 1024 fmt=1
[TFAtlas] page 3 created: 1024 x 1024 fmt=1
[TFAtlas] page 4 created: 1024 x 1024 fmt=1
```

* 设备最大纹理只有 **1024×1024**，而整套美术按像素格式分需要 **5 页**；
* 绘制顺序在页与页之间来回跳（僵尸部件、植物、粒子各自落在不同页）
  → 相邻精灵很少同页 → 按 (纹理, 混合模式) 合批仍然频繁打断。

**而且**：混合模式变化、纹理滤镜变化、任何其它绘制路径都会强制 flush —— 每一次都拆一批。
所以"张数变成个位数"的前提是**绘制顺序被重排成同页连续**，而重排会改变层叠顺序
（同一格上叠种的植物、南瓜壳的覆盖关系都依赖顺序）→ **不能随便重排**。

### 12.3 已经拿到的确定价值

1. **管线打通并验证**：装箱器（0 重叠 / 73.2% 占用）+ 目标偏移拷贝 + 页内绝对 UV +
   `ReleaseTextures` 不再误放共享页 —— 全部实机跑通，**截图逐像素核对画面正常**（选卡图标/僵尸/植物/阳光/UI 均正确）；
2. 8% 的真实调用数下降；
3. 一套**可复用的正确性纪律**：整图全成功才入图集（避免半图集半独立纹理）、
   图集拷贝禁用 padding hack（会踩邻居格子）、失败整图回退。

### 12.4 踩过的坑（给后来者）

* 我一度以为"开图集就在加载期崩溃"——**其实是自己的两个测试脚本并发跑、互相把对方的游戏进程杀掉了**，
  报告里出现的 `EXITED during load` 是假象。**教训：性能基准必须串行跑，并且要能区分"真崩"与"被自己杀掉"。**
* 诊断方式很有效：`thirtyflags_atlas.log`（页创建/尺寸/失败点）+ 设备上限一行日志，
  一跑就知道是"没调用"还是"调用了但失败"。

### 12.5 修正后的下一步（按性价比）

1. **减少四边形数量**（唯一还有确定空间的方向）：继续做"重复表现去重"、
   静态图层合并、审计同格多株植物的重复粒子；
2. **按页重排绘制**：只对**视觉上与顺序无关的组**做（例如加色粒子/拖尾这类
   本来就无遮盖语义的效果）→ 把它们按页聚到一起画，才能吃到合批红利。
   **这是给"帅特效"留的正路**：特效自己成组、自己按页排，不影响主渲染顺序；
3. 更大页（2048²）**做不到**：设备上限就是 1024。


## §13 表现层特效层：把"合批红利"用在特效上（§12 结论的正解）

### 13.1 设计（对应 §12 的三条约束）

| §12 的约束 | 特效层的做法 |
|---|---|
| 同纹理才能合批 | **只用两张现成贴图**：`IMAGE_SPOTLIGHT`（软光晕）/ `IMAGE_WHITEPIXEL`（实心四边形）→ 零新资源 |
| 同混合模式才不拆批 | 整层**只用加色**（`DRAWMODE_ADDITIVE`），中间不换模式 |
| 重排会破坏层叠顺序 | 特效之间是加色叠加、**无遮盖语义** → **允许按类型成组**，不影响主渲染顺序 |

实现要点：`TfFxQuad` 池（384 个）+ 池满覆盖"寿命最短"的一个（保证新事件一定可见）+
**按 kind 分组绘制**（每 kind 一张贴图、一遍连续绘制）→ 每类所有特效合并成极少数次提交。

### 13.2 已接入的触发点

* **命中光晕**：僵尸受伤时（约 1/3 概率，避免刷屏）→ 小暖色光晕；
* **击杀冲击波**：僵尸死亡 → 一圈大而慢的白光 + 一层暖色余晖；
* 调试版另有一个**自测发射**（每 90 帧在草坪上放一组，用于与战斗无关地验证管线）。

### 13.3 验证结果（可量化）

加入自测发射后：`sprite=976/831` → **`sprite=979/833`**
→ **3 个额外四边形只多 1~2 次绘制调用**，证明"同图同模式的特效确实被合并提交"（正是 §12 说的正解）。

⚠️ **遗留**：肉眼截图确认**未完成** —— 我的自动化运行里游戏停在「继续游戏?」弹窗上
（该弹窗不处理键盘、我按坐标点击也没能关掉），特效被弹窗挡住拍不到。
**这是测试基础设施的待办，不是特效本身的问题**（计数已经证明在画）。
下一步：给采样脚本加"识别并关闭弹窗"的能力（或直接改走"无存档 → 不弹窗"的启动路径）。


## §14 测试环境取证：存档到底在哪（顺带解开三个自相矛盾的结论）

### 14.1 取证过程

在 `LawnApp::TryLoadGame()` 里加一行日志，把「读档路径 + 是否存在」打出来：

```
[PreNewGame] PreNewGame mode=71
[PreNewGame] TryLoadGame mode=71 dataFolder=[C://ProgramData////PlantsVsZombies//]
             path=[C://ProgramData////PlantsVsZombies//userdata//game2_71.dat] exists=1
```

### 14.2 三个被这行日志纠正的结论

| 我先前说过 | 真相 |
|---|---|
| "三十旗自动存档没在写"（因为找不到 `game*_71.dat`） | **错。存档一直在写**，只是目录是 `C://ProgramData//PlantsVsZombies//userdata//`（**没有 `PopCap Games\` 这一层**），我一直在错目录里找 |
| "`GAMEMODE_THIRTY_FLAGS` = 73"（我靠数枚举项得出） | **错，是 71**（日志里的运行时值才是权威）。数枚举这种做法不可靠 —— 枚举可能有显式赋值 |
| "游戏可能卡在某个不可解释的弹窗" | 那个弹窗正是原版 `[CONTINUE_GAME]`（"继续/新游戏"），**只在读档成功时出现** → 它是"有存档"的正常表现，不是 bug |

> 教训：**枚举值 / 路径这类事实，去跑一次打日志，不要靠数、不要靠猜。**
> 我在这上面来回错了三次（71→"没存档"→73→71），成本远高于加一行日志。

### 14.3 顺手解决的测试障碍

那个 `[CONTINUE_GAME]` 弹窗会**吃掉所有按键**（模态弹窗不处理键盘，PostMessage 点击也无效），
导致之后 `q` 铺场、推旗全部失效 → 我的采样一直停在 `pl=3`、没有战斗、看不到命中类特效。

**解决办法**：跑测试前把 `game2_71.dat` / `.tf` **改名挪开**（游戏就看不见存档 → 不弹窗），
跑完**还原并 MD5 校验**（本次已校验一致，玩家进度零损失）。
之后同一次采样立刻变成 `z=70 / pl=6`（战斗场面），按键全部生效。
