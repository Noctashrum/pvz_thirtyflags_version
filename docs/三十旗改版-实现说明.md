## 1. 怎么进入这个模式

| 入口 | 路径 |
|---|---|
| **正式入口** | 主菜单 → 解谜/挑战页（Limbo 附加页）→ 第 3 行第 4 列的「三十旗」按钮（向日葵图标，常驻解锁） |
| **标题画面** | 标题画面直接按 **`T`** 进入三十旗（无门槛；`mTodCheatKeys` 在 Release 下不存在，故单开） |
| **选卡画面** | 按 **`S`** 随机选满 10 张卡并直接开战（同上，无门槛） |
| **局内键** | **`Tab`** 直接跳到第 30 旗（僵王终战）；**`.`** 推进一旗；**`,`** 清场结束当前旗 |

> `.` / `,` 原本挂在 `mTodCheatKeys` 下，而该开关只在 `#ifdef _DEBUG` 的 `-tod` 命令行分支里被置位，
> **Release 下永远为 false**——也就是说这两个键此前在本工程的 Release 构建里从未生效。现已去掉该门槛。


模式实现为新的 `GameMode::GAMEMODE_THIRTY_FLAGS`（枚举值 72，插入在 `GAMEMODE_UPSELL` 之前），
并在 `gChallengeDefs` 表尾追加一条定义（数组长度随之 +1，`下标 = 枚举值 - 1` 的既有规则保持不变）。

## 2. 架构：一个模块 + 若干钩子

设计上刻意**不把三十旗逻辑散进 Board/Zombie/Plant**，而是：

```
ThirtyFlags.h/.cpp      ← 全部规则、数值表、单局状态、以及派生系数
      ▲
      │ 钩子调用（进入非三十旗模式时全部零开销，函数首行即 return）
      │
Board.cpp  LawnApp.cpp  Zombie.cpp  Plant.cpp  TFDialog.cpp
```

### 2.1 关键设计决策

| 决策 | 原因 |
|---|---|
| 三十旗复用「生存模式」基础设施 | `IsSurvivalMode()` 对三十旗返回 true，直接复用原版的**每旗重选卡**（`InitSurvivalStage` + `SeedChooserScreen` 的 SurvivalRepick 路径）、阶段推进与存档点，省掉一整套自研流程 |
| 旗次的**唯一数据源**是 `Board::mChallenge->mSurvivalStage + 1` | 不能只依赖 `gThirtyFlags.mFlag`：`Board::InitSurvivalStage` 会在 `mSurvivalStage` 自增**之前**调用 `InitZombieWaves`，此时按 `mFlag` 会取到上一旗。`mSurvivalStage` 全程等于「已完成旗数」，任何时机都正确（统一由 `ThirtyFlagsCurrentFlag()` 提供） |
| 固定使用**泳池背景** | 水面与陆地共存，且行高 85px 与网格换算自洽；白天背景（行高 100px）混水陆会导致僵尸/植物 y 坐标错位 |
| 精英词条借用 Boss 专用字段 | `Zombie` 类没有空闲成员。`mBossMode`（词条位掩码）、`mBossBungeeCounter`（护盾计时）、`mBossStompCounter`（投矛计时）、`mVelZ`（移速倍率）**只在 `ZOMBIE_BOSS` 分支被读写**，三十旗的所有精英逻辑都显式排除 Boss，因此不会冲突，也就无需改动 `Zombie.h` 的成员布局（存档 `SyncBoard` 按 `sizeof(Board)` 整体写盘，改结构会破坏存档兼容） |
| 植物增伤用 `DamageFlags` 的 bit 8 标记来源 | `Zombie::TakeDamage` 是唯一的受伤入口，在此处统一结算攻击力加成/暴击/穿甲/铁壁/尸甲。原版 `DamageFlags` 只用到 bit 0..5，bit 8 空闲 |
| 攻速实现为**缩短发射间隔** | 不新增计时器：`Plant::UpdateShooter` 里把 `mLaunchCounter` 的每帧递减量按攻速倍率放大，等效缩短冷却 |
| 整备弹窗复用原版 `ToolTipWidget` 显示中文 | 工程内置字体在拉丁字形之外**也含中文字形**（全工程显示中文走的都是 `Graphics::DrawString`），无需自造点阵字库。注意 `ToolTipWidget` 不是 `Widget`，不能挂进控件树，必须在其父对话框的 `Draw` 里手动绘制 |

## 3. 策划案逐条落地情况

### 3.1 场地：动态扩展与水路（第 2 章）— 已实现

`ThirtyFlagsFlagDef` 表（`ThirtyFlags.cpp` 顶部）逐旗声明 `mUnlockedRows`（行位掩码）、`mWaterRows`、`mWaterCols`、`mFogCols`。

日间布局只有 5 行可用（第 6 行 y≈580 已出画面），所以**行解锁节奏是「中间 1 道 → 4 道陆地 → 两端转水路」**：

| 旗帜 | 场地变化 | 掩码 |
|---|---|---|
| 1–3 | 只开放第 3 行（正中 1 道，真 1-1 观感） | `TF_R2` = `0b00100` |
| 4–7 | 开放第 2 行（共 2 道） | `TF_R2 \| (1<<1)` = `0b00110` |
| 8–12 | 开放第 4 行（共 3 道，「三线成形」） | `TF_R1_3` = `0b01110` |
| 13–17 | 开放第 1 行（共 4 道，「四线铺开」） | `(1<<0) \| TF_R1_3` = `0b01111` |
| 18–30 | 开放第 5 行，第 5 行整行转水（「水路登场」） | `TF_R0_4` = `0b11111` |
| 20 起 | 第 1 行同时转水（「双向水路」） | `mWaterRows = (1<<4)\|(1<<0)`，`mWaterCols = MAX_GRID_SIZE_X` |
| 15 起 | 右侧 3 列持续迷雾 | `mFogCols = 3`，写入 `mGridCelFog`，并让 `StageHasFog()` 成立以便路灯花生效 |

> 行的位掩码 `bit0…bit4` 依次对应第 1…5 行。未开放行写入 `PLANTROW_DIRT` + `GRIDSQUARE_DIRT`（不可种植，黑幕由 `DrawBackdrop` 绘制）。
> **每次行扩展的那一瞬间还会补放该行的小推车** —— 见 §3.11。

水路规则全部由 `mGridSquareType` / `mPlantRow` 驱动，因此**睡莲前置、睡莲被吃连带其上植物死亡、潜水僵尸需反隐、海豚越位**这些原版机制**无需额外代码**即自动生效。
`IsWaterCell(row, col)` 是「某格是否水」的唯一判定，行 = `PLANTROW_POOL`（水陆行在泳池布局下坐标自洽），格 = `GRIDSQUARE_POOL`（仅右侧 N 列）。

### 3.3 尸潮进化（第 4 章）— 已实现

| 层 | 实现 |
|---|---|
| **数值成长** | `Zombie::ZombieInitialize` 末尾把 `mBodyHealth` / `mHelmHealth` / `mShieldHealth` / `mFlyingHealth` 与最大值同乘 `GetHealthScale()`（每旗 +7%，上限 6.8×）。移速由 `ThirtyFlagsBoardUpdate` 逐帧乘算施加（每旗 +1.5%，上限 +45%）—— 逐帧施加是必须的，否则会被 `Zombie::PickRandomSpeed()` 覆盖 |
| **突变（每 5 旗抽 1 条）** | 8 条全部实现：尸爆（`KillAllPlantsInRadius`）、尸毒（独立毒潭计时表，每 25 帧对该格植物造成伤害）、吸血（`EatPlant` 后按最大生命 2% 回复）、尸甲（`TakeDamage` 减伤 15%）、疾行（移速 +25%）、增殖（30% 概率原地留小鬼）、掘地（原地留 `GRIDITEM_CRATER`，`mGridItemCounter = 150` 即原版的「该格 15 秒不可种植」）、共鸣（场上僵尸数 × 1% 攻击力） |
| **精英化（第 16 旗起）** | 7 条词条全部实现：迅捷（+60% 移速）、护盾（每 480 帧 = 4.8 秒 300+10% 最大生命）、再生（**每秒 2%**，见下方勘误）、铁壁（受伤 −40%）、分裂（死亡分裂 2 个半血小鬼）、投矛（每 300 帧 = 3 秒直伤最前排植物并投出刺的视觉表现，投掷后有硬直避免刷矛）、狂暴（生命 < 30% 后每帧啃两口）。精英概率 15% 起步，逐旗 +3%，上限 60%；单只最多 3 条 |

> **勘误（2026-10-03 实测修正）**：`再生` 原本按 `mZombieAge % 10 == 0` 触发。
> `mZombieAge` 在 `Zombie::Update()` 里**每帧 +1**，而后端是 100 帧/秒，
> 于是实际是「每秒回复 2% × 10 = **20% 最大生命**」——是设计稿「每秒 2%」的 10 倍。
> 后果：任何低 DPS 手段（忧郁菇 40 DPS、猫尾草 40 DPS）都被完全回复掉，
> 精英僵尸对它们等效无敌。现已改为 `% 100 == 0`（每秒 2%）。
> **这是一处与设计稿的偏离修正**，若确实希望精英更肉，改回 `% 10` 即可（见 `ThirtyFlagsZombieUpdate`）。

### 3.4 僵尸本体改造（第 5 章）— 部分实现（**逐僵尸 AI 分支改造本轮仍未落地**）

策划案第 5 章逐条改造约 25 种僵尸。**本次实现的是能由通用钩子覆盖、且不改 AI 的部分**：

> 本轮并行任务中的「僵尸本体」改造，经代码核对（`src/Lawn/Zombie.cpp` 内除下列通用钩子外，
> 未见针对单种僵尸 AI 分支的新增改动），**尚未落地**。因此 §8 中的「第 5 章 13 条」仍列为未实现。
> 已落地的僵尸侧能力如下（均为通用通道）：

- **生效中（精英词条等价覆盖）**：迅捷/铁壁/再生/护盾/分裂/投矛/狂暴七条词条，恰好对应策划案 4.3 的精英表；僵尸全员生命与移速成长；植物僵尸通过 `BuildZombieMask` 在第 26/29 旗起登场（纯耐久检验）；红眼巨人与冰车在后期登场。
- **由突变机制等价覆盖**：「僵尸成群后不再脆弱」→「共鸣」；「一次漏防长期生效」→「掘地」坑洞；「僵尸攻击植物时回复」→「吸血」；「死亡时爆炸」→「尸爆」。
- **未实现**（需要改各僵尸的专有 AI 分支，属于「不改基础 AI」原则的边界）：铁桶卸甲后狂暴、铁门+铁桶双层护甲、橄榄球头盔免疫减速、读报破报后碾压与吟唱无敌、撑杆失去撑杆后碾压、蹦蹦越过任意高度与离场召尸潮、气球击落 3×3 爆炸、矿工隧道口、雪橇队共享生命条与生成墓碑、梯子铺满整行、小丑爆炸范围 5×5、投石车免疫减速、巨人砸击无敌帧。

> 第二个参数 `theLookForSavedGame` 为假 —— 盘一直在写，只是从来没人去读。

### 3.10.2 改动清单

| 文件 | 改动 |
|---|---|
| `GameSelector.cpp` / `LawnApp.cpp`（`DIALOG_TF_ENTER`） | `PreNewGame(GAMEMODE_THIRTY_FLAGS, false)` → `true`，开始寻找存档 |

| `Board::KeyChar` 的 Backspace / Delete | 由 `remove("thirtyflags_save.ini")` 改为 `ThirtyFlagsClearSave()`，再 `PreNewGame(..., false)` 重开 |

### 3.10.3 `<存档>.tf` 附加文件

`Board` 的布局**不能加成员**（`SyncBoard` 按 `sizeof(Board)` 整块写盘，改结构会破坏兼容），
而 `ThirtyFlags` 全局对象又不在 `Board` 里。所以肉鸽层单独写一个小二进制文件 `game71_<id>.dat.tf`，
紧跟 `LawnSaveGame` / `LawnLoadGame` 写入和读取，两个文件同生共死。

落盘字段（见 `ThirtyFlags.cpp` 的 `RUN SAVE` 段）：旗次、突变词条与剩余抽取次数、35 个强化的层数、
传说计数、整备期状态（`mIntermission` / `mUpgradeChosen` / `mPrepTimeLeft` 等）、击杀数、失守行数、
Boss 阶段、NIRVANA 待复活植物表、尸毒潭表。

### 3.10.4 读档时的三个补牢点

1. **`Board::InitLevel()` 在读档路径上不会执行**，因此 `ThirtyFlagsInitRun()` 也不会跑。
   `ThirtyFlagsOnLoadGame()` 负责重建 `gThirtyFlags`：`mActive = true`、
   `ApplyFlag(ThirtyFlagsCurrentFlag(board))`、重算草皮 / 水面淡入等表现层。
2. **实体指针在重载后全部失效**。`gThirtyFlags.mBossPtr` 被置空，并给 `TFBossResolve()`
   加了「缓存失效时扫描 `ZOMBIE_BOSS`」的兜底 —— 否则第 30 旗读档会再刷一只僵王。
3. 对话框无法跨进程存活。读档时若处于整备期且尚未选卡，会把 `mUpgradeDialogShown` 置回 `false`，
   让三选一弹窗重新出现。

### 3.10.5 玩家视角

进入三十旗时若存在存档 → 弹出原版「继续游戏？」对话框：
**继续**（接着上一旗打，场上植物 / 阳光 / 小推车全部保留）、**新游戏**（清档从第 1 旗重来）。
游戏中按 `Backspace` / `Delete` 直接清档重开；退出游戏（返回主菜单 / 关窗口）也会自动存档。


## 3.11 小推车：原版为什么不建、怎么补

行扩展时「小推车不出现」曾经反复修不好，根因不在「车没被创建」，而在**原版创建出来的车是停在屏幕外的**。

### 3.11.1 原版的车是怎么进场的（三步，缺一不可）

| 步 | 位置 | 说明 |
|---|---|---|
| 1 | `CutScene::PlaceLawnItems()` → `Board::InitLawnMowers()` | **唯一**建车入口，且被 `if (!IsSurvivalRepick())` 挡住 |
| 2 | `LawnMower::LawnMowerInitialize()` | 把 `mPosX` 设成 `-160`（屏幕外）、`mVisible = false` |
| 3 | `CutScene::Update()`：`aLawnMower->mVisible = true; mPosX = CalcPosition(..., -80, -21)` | **唯一**把车挪进场的代码，同样被 `if (!IsSurvivalRepick())` 挡住 |

`CutScene::IsSurvivalRepick()` = `IsSurvivalMode() && mChallenge->mSurvivalStage > 0 && mGameScene == SCENE_LEVEL_INTRO`。
三十旗 `IsSurvivalMode()` 为真，且第 2 旗起 `mSurvivalStage > 0` —— 所以**第 2 旗之后原版再也不建车、也不把车挪进场**。

> 之前几轮修复之所以看上去无效：只做了第 1 步（`DataArrayAlloc` + `LawnMowerInitialize`），
> 于是车确实被建出来了，但永远停在 `mPosX = -160` —— 肉眼就是「小推车不出现」。

### 3.11.2 修复：自己把车送到位

`TFSpawnLawnMower(board, row)`（`ThirtyFlags.cpp`）：

```cpp
aMower->LawnMowerInitialize(theRow);                        // mPosX = -160（屏外）
aMower->mVisible = true;
aMower->mRollingInCounter = 0;
aMower->mMowerState = LawnMowerState::MOWER_ROLLING_IN;      // 走原版入场动画
```

关键是最后一行：`LawnMower::Update()` 的 **`MOWER_ROLLING_IN` 分支在 `mGameScene != SCENE_PLAYING` 的早退之前**，
所以它会用 100 帧把 `mPosX` 从 `-160` 插值到 `-21`，然后转 `MOWER_READY`。
这条路径是原版自己就在用的（`LawnMower::Die()` 为「奖励小推车」重建时也是这么写的），不是自创。

### 3.11.3 什么时候补：每帧安全网 + `granted` 位图

`TFEnsureRowLawnMowers()` 挂在 `ThirtyFlagsUpdateSod()` 里，**每帧**扫一遍 5 行：
已解锁 且 从未发过车 且 该行当前没有车 → 补一辆。

不用「只在解锁那一帧补一次」，是因为有两条路会漏：

* 解锁那一帧 `mPlantRow` 可能还没从 `PLANTROW_DIRT` 改过来，补车会被条件挡回去；
* **读旧存档进入时，已解锁的行根本不会走「新解锁那一帧」** —— 这正是「存档里的扩展行永远没车」的原因。

「已经发过车」记在 `gThirtyFlagsMowerGranted`（位图，随 `<存档>.tf` 落盘）。
不用幂等补齐是为了玩家：**丢车之后不会下一帧凭空复活**；
而位图读旧档时为 0，所以旧档里缺的车会被补回来（一次性，之后正常记账）。

安全网门槛是 `mGameScene == SCENE_PLAYING`，避免在第 1 旗的开场演示（`SCENE_LEVEL_INTRO`）里
和原版 `InitLawnMowers()` 抢着建车、造成同一行两辆车。

### 3.11.4 实测证据

`docs/mower/`（回归脚本产物，已 gitignore）与 `Release\thirtyflags_flow.log`：

```
[TFMower] AdvanceFlag: stage=3 -> flag 4
FlagChanged -> flag 4 (rows=6)              ← 掩码 6 = 第 2、3 行，第 2 行是新解锁的
[TFMower] row 1 unlocked, plantRow=1 hasMower=0
[TFMower] spawn row=1 posX=-160.0 visible=1 state=0
                                               ↑ state 0 = MOWER_ROLLING_IN
```

对应截图（`docs/mower/auto-flag4.png` / `auto-flag5.png`）：第 4 旗时新行还没车、
第 5 旗时第 1、2 行**两辆车都已经停在场内左侧**。


## 3.12 忧郁菇「孢子腐化」+ 猫尾草「收割」

这两个植物原本只有数值改动，打精英仍然吃力。原因是**数值解决不了机制问题**：
精英「再生」的回复是比例回血，DPS 不够就永远打不死；而忧郁菇/猫尾草恰好都是低 DPS、
高覆盖的代表（范围 / 全屏追踪）。所以这里给它们各加一条**真机制**，而不是继续堆数字。

### 3.12.1 忧郁菇 —— 孢子腐化（`ThirtyFlagsAddCorrupt` / `ThirtyFlagsGetCorrupt`）

孢子命中的僵尸获得「腐化」层数（最多 `TF_CORRUPT_MAX_STACKS` = 4 层，
每层 `TF_CORRUPT_DURATION` = 6 秒，命中刷新）：

| 效果 | 实现位置 |
|---|---|
| **禁止一切回复**：精英「再生」失效 | `ThirtyFlagsZombieUpdate` 的 `ELITE_REGEN` 分支加 `GetCorrupt == 0` |
| **禁止护盾**：精英「护盾」失效 | 同函数 `ELITE_SHIELD` 分支 |
| **禁止吸血**：突变「吸血」与尸王领域吸血失效 | `ThirtyFlagsZombieAtePlant` 的吸血块 |
| 每层 −12% 移速（4 层 −48%） | `ThirtyFlagsBoardUpdate` 的逐帧移速乘算 |

> 这是「打不动精英」的**机制解**：忧郁菇不跟精英比 DPS，而是直接把对方的回血关掉。
> 副作用是它也顺手克制了突变「吸血」和尸王领域的吸血 —— 属于合理的设计联动。

**施加点**：`Plant::DoRowAreaDamage` 里 `SEED_GLOOMSHROOM` 命中判定之后
（只对真正被打到的僵尸生效，不是全屏乱贴）。

### 3.12.2 猫尾草 —— 收割（`ThirtyFlagsHarvestPercent`）

| 效果 | 说明 |
|---|---|
| 刺带「破绽」标记 | 复用豌豆的标记系统：`Plant::Fire` 里给猫尾草的弹体也设 `mElement = TF_ELEM_MARK`，命中叠层（每层 +5% 受伤，最多 5 层） |
| **对腐化目标 ×2** | `TF_HARVEST_CORRUPT_PCT` |
| **对精英僵尸 ×1.5** | `TF_HARVEST_ELITE_PCT`，与上一项**相乘**（同时满足 = ×3） |
| 结算位置 | `Projectile::DoImpact` 的直伤分支：`mProjectileType == PROJECTILE_SPIKE && mElement == TF_ELEM_MARK`（只有猫尾草同时满足；仙人掌的刺不走这条） |

于是有了明确的组合：**忧郁菇腐化 → 猫尾草收割**。
这也是为什么两个植物的**基础数值只给了 3~4 倍**（见 §4.1）——强度主要来自机制。

> 存储方式沿用工程约束：**不给 `Zombie` 加成员**（`SyncBoard` 按 `sizeof(Board)` 写盘），
> 腐化状态用文件级 `static int` 数组按 `Board::ZombieGetID()` 索引，
> 并在 `ThirtyFlagsTickCorrupt()` 里逐帧递减超时清理（与破绽标记同款）。


## 3.13 南瓜头「套住植物」的 −50% 到底是给谁打的

策划案第 6.2 章原文只有一句：

> **南瓜头**：护甲 4000 → 8000；**被南瓜套住的植物**，其阳光消耗与冷却 −50%。

关键在**主语是「被南瓜套住的植物」**，不是南瓜头自己。早期实现把这句话读成了
「南瓜头费用/冷却 −50%」，并且写成了**无条件**打折（种在空地上也打折），
与策划案不符。现已按原文改正：

| | 改动 |
|---|---|
| 南瓜头自身 | **恢复原价 / 原冷却**（`Board::GetCurrentPlantCost` 与 `SeedPacket::WasPlanted` 里的无条件 −50% 已删除） |
| 被套住的植物 | 阳光与冷却各 −50% |

### 3.13.1 「被套住」在代码里是哪一种情况

本改版有两类「南瓜 + 植物同格」的顺序：

1. **先种植物 → 再用南瓜套住**：这株植物在成为「被南瓜套住」之前，**钱和冷却就已经付过了**，
   无法追认折扣。这种情况不享受打折。
2. **先铺南瓜 → 再往南瓜格里种植物**：本改版的叠种机制允许这样做
   （`Board::CanPlantAt` 的 `if (aPumpkinPlant && aSameCell <= 2) return PLANTING_OK;`）。
   这时种下去的植物才是真正「被南瓜套住」的，**享受 −50%**。

于是这条机制在玩法上等价于：**奖励「先铺南瓜、再往里面种」的建造顺序**。

### 3.13.2 实现位置

| 项 | 位置 |
|---|---|
| 判定 | `ThirtyFlagsIsPlantingIntoPumpkin(board, gridX, gridY, seedType)`：目标格有南瓜（`Board::GetPumpkinAt`）且种的不是南瓜头/模仿者 |
| 阳光 | `Board::MouseDownWithPlant` 的扣费处：`aCost = GetCurrentPlantCost(...); if (套住) aCost /= 2;` |
| 冷却 | 同函数 `...WasPlanted()` 之后：`mSeedPackets[idx].mRefreshTime /= 2;`（`mRefreshTime` 是 `SeedPacket` 的公开成员） |

> 顺带说明：卡面显示的是**原价**（`DrawSeedPacket` → `GetCurrentPlantCost`）。
> 因为折扣取决于「你往哪个格子种」，而卡片绘制拿不到光标所在格。
> 之前卡面还恒显示 `Plant::GetCost`，已改为 `GetCurrentPlantCost`，
> 至少能把三十旗的「费用缩放」正确显示出来。


## 3.14 叠种 × 紫卡限制 / 猫尾草顶种（两处回归修复）

实测反馈：「紫卡限制好像又超了，原本只是让猫尾草无限制，结果机枪豌豆和双子向日葵
好像都能直接种植了」，以及「在南瓜头里叠种金盏花 + 猫尾草时，猫尾草把金盏花顶掉了」。

### 3.14.1 紫卡限制被叠种路径绕过

`Board::CanPlantAt` 里守卫紫卡的检查（`Plant::IsUpgrade(theSeedType)` → `PLANTING_NEEDS_UPGRADE`）
**在 `if (aNormalPlant)` 块之外**，而三十旗的叠种规则是在**该块之内**提前 `return PLANTING_OK`：

```cpp
if (aNormalPlant)
{
    if (ThirtyFlagsMode())
    {
        if (Plant::IsUpgrade(theSeedType)) { /* 扫描同格可升级目标，找到才 return OK */ }
        ...
        if (aPumpkinPlant && aSameCell <= 2)  return PlantingReason::PLANTING_OK;   // ← 后门
        if (aNormalPlant->mSeedType == SEED_SUNSHROOM && aIsProducer && aSameCell <= 1)
                                              return PlantingReason::PLANTING_OK;   // ← 后门
    }
```

于是「南瓜格可叠种任意植物」「阳光菇格可叠种产能植物（含双子）」这两条规则
**顺带把紫卡的前置限制也一起放行了** —— 在南瓜格里可以直接种机枪豌豆，
在阳光菇格里可以直接种双子向日葵，全都不需要底座。

**修复**：在那轮扫描之后、两条叠种放行之前，补一道守卫 ——
升级卡（猫尾草除外）若没扫到可升级目标，直接 `PLANTING_NEEDS_UPGRADE`：

```cpp
if (Plant::IsUpgrade(theSeedType) && theSeedType != SeedType::SEED_CATTAIL)
{
    return PlantingReason::PLANTING_NEEDS_UPGRADE;
}
```

保留的行为：
- 猫尾草仍然完全无限制（唯一例外）；
- 南瓜格/阳光菇格**非紫卡**的叠种照旧；
- 真升级不受影响：南瓜 + 双发 → 机枪豌豆、阳光菇 + 向日葵 → 双子向日葵 依然可行
  （扫描能扫到可升级目标）。

### 3.14.2 猫尾草把同格植物顶掉

`Board::MouseDownWithPlant` 里有一块**原版遗留**：

```cpp
if (aPlantingSeedType == SeedType::SEED_CATTAIL)
{
    if (aPlantOnLawn.mUnderPlant)  aPlantOnLawn.mUnderPlant->Die();
    if (aNormalPlant)              aNormalPlant->Die();     // ← 把金盏花删了
}
```

原版猫尾草是「睡莲升级」，种下来会把睡莲**和睡莲上面那株植物**一起清掉，这是对的。
但三十旗已经把猫尾草改成普通植物（解除睡莲前置），这块就成了纯 bug：
在南瓜格里叠种「金盏花 + 猫尾草」时，金盏花被无条件删除。

**修复**：整块加 `&& !ThirtyFlagsMode()` 门槛。
睡莲 → 猫尾草的真升级仍由上面的 `aUpgradeTarget` 分支处理（会正确删掉睡莲）。

修复后在南瓜格里种猫尾草，同格变成 **南瓜 + 金盏花 + 猫尾草**（3 株，符合叠种上限）。

### 3.14.3 已知未处理的相邻情况

`CanPlantAt` 在 `aUnderPlant`（睡莲/花盆）分支里，对猫尾草仍保留
`if (aNormalPlant) return PLANTING_NOT_HERE;`（原版「猫尾草不能盖在有植物的睡莲上」）。
三十旗里理论上也应该允许，但那条路径会顺带把睡莲删掉、有可能影响睡莲上的植物，
**风险大于收益，暂未改动**。如果实测确实需要，再单独处理。


## 3.15 「植物莫名其妙消失」——不是 bug，但确实是设计缺陷

实测反馈：「场上的植物会莫名其妙消失，一点特效都没有」。排查结论：
**不是引擎 bug，是突变「尸爆」的实现在"可读性"上是失败的**，另外还有一处**完全没画出来**的机制。

### 3.15.1 元凶：突变「尸爆」

```cpp
if (HasMutation(MUTATION_ZOMBIE_EXPLODE))
{
    theBoard->KillAllPlantsInRadius(theX, theY, 90);   // ← 原实现
}
```

两个问题叠加：

| 问题 | 后果 |
|---|---|
| `KillAllPlantsInRadius` 内部**只有 `aPlant->Die()`，没有任何粒子/音效** | 植物**瞬间消失且零反馈** |
| 它是**无条件秒杀**，而不是策划案写的「对周围植物**造成伤害**」 | 半径 90px（≈1.1 格）内的植物不分血量一律清空 —— 16000 血的高坚果也秒 |

于是玩家的体验就是「植物凭空没了」，且完全无法归因 —— 这正是反馈里说的现象。

**修复**（`ThirtyFlags::OnZombieKilled`）：

1. **先放可见特效**：`PARTICLE_JACKEXPLODE`（原版小丑僵尸爆炸粒子，语义贴合「尸体爆炸」）；
2. **改成伤害结算**：`mPlantHealth -= TF_EXPLODE_DAMAGE`（200），
   血量厚的植物能扛住，脆皮射手会被炸掉 —— 与策划案「造成伤害」一致；
3. **落日志**：`[TFPlant] explode at px=(x,y) dmg=200 killed=N` 写进
   `Release\thirtyflags_flow.log`，下次再遇到可以直接查是谁干的。

### 3.15.2 附带修掉的：尸毒潭从来没被画出来

`gThirtyFlagsPoison[col][row]` 只在两处被读：递减计时、每 25 帧扣 4 点植物血。
**`ThirtyFlagsDrawVisuals` 里没有任何绘制** —— 也就是说「尸毒」这个突变
只有伤害、没有任何视觉，玩家看不到哪一格有毒。

**修复**：在 `ThirtyFlagsDrawVisuals` 开头按格绘制半透明毒潭（绿色矩形 + 呼吸环，
alpha 随剩余帧数变化），毒潭终于可见。

### 3.15.3 顺手补齐的其他「无声删除」

同一类问题（删植物但玩家看不出原因）在这几处也补了反馈：

| 位置 | 原来 | 现在 |
|---|---|---|
| `TFBossDoSlam`（P1 砸击） | 有雷声，但被砸植物无声消失 | 加 `PARTICLE_BLASTMARK` 爆点 |
| `TFBossDoRoarUltimate`（P3 咆哮） | 整列植物无声消失，只有雷声 | 每株加 `PARTICLE_BLASTMARK` |
| `TFBossDoTerrain`（P2 地形转水） | 非睡莲植物无声淹死 | 每株加 `PARTICLE_POOL_SPLASH` 水花 |
| 毒潭致死 | 无 | 加 `[TFPlant] poison killed plant ...` 日志 |

### 3.15.4 结论：这类"消失"只有这几个来源

排查时按这个清单对，不要怀疑引擎：

| 来源 | 有无反馈 | 备注 |
|---|---|---|
| 突变「尸爆」 | ✅ 爆炸粒子（本次修复） | 半径 90px，500 伤害 |
| 突变「尸毒」 | ✅ 毒潭（本次修复） | 每 25 帧 4 点，总量不大 |
| 突变「掘地」 | ✅ 地面坑洞 | **不杀植物**，只让该格 15 秒不能种 |
| 精英「投矛」 | ✅ 投出的刺 | 每 3 秒对最前排植物 100 伤害 |
| 僵王三阶段技能 | ✅ 本次补齐 | 仅第 30 旗 |
| 铲子 / 升级替换 / 南瓜替换 | ✅ 玩家主动操作 | |

**行转水路（第 18 / 20 旗）不会淹死植物** —— `Plant.cpp` 里没有任何 `PLANTROW_POOL`
相关判定，已核对。


## 3.16 「直接伤害」全面削弱 + 南瓜头当护甲

实测反馈：「把这些直接伤害削弱一下，如果植物套在南瓜里面就不会受伤吧，不然太强了」。

### 3.16.1 两条通用规则

原先这些机制都是**绕开正常防御结算的无条件删除/秒杀**，血再厚也没用。现在统一成立两条规则：

| 规则 | 说明 |
|---|---|
| **① 扣血，不秒杀** | 全部改成 `mPlantHealth -= 伤害`，血量厚的植物扛得住；只有脆皮会被直接带走 |
| **② 南瓜头当护甲** | 该格有南瓜头时，伤害**全部由南瓜先吃**，套在里面的植物一点血不掉 |

规则② 也是 PvZ 里南瓜的设计意图（僵尸先啃南瓜）。实现收口在两个函数里：

```cpp
// 某格「直接伤害」的承伤对象：有南瓜就是南瓜，否则是该格的普通植物
static Plant* TFDirectDamageTarget(Board* theBoard, int theGridX, int theGridY);
// 对半径内的「格子」各结算一次（每格只打一次，避免南瓜被同格多株植物重复转发）
static int    TFDirectDamageInRadius(Board* theBoard, int px, int py, int radius, int damage);
```

配套策略：**猫尾草的「收割」不会被南瓜挡**（它本来就是打僵尸的）。
反过来，`尸爆 / 尸毒 / 精英投矛 / 僵王技能` 全部走上面两个入口。

### 3.16.2 逐项数值改动

| 机制 | 原来 | 现在 | 常量 |
|---|---|---|---|
| 突变「尸爆」 | 半径 90px **无条件清空**，零特效 | 半径 90px，**200 伤害** + 爆炸特效 | `TF_EXPLODE_DAMAGE` = 200 |
| 突变「尸毒」 | 每 25 帧 **4 点**（逐株结算） | 每 25 帧 **3 点**，**按格**结算（每格只打一次） | `TF_POISON_TICK_DAMAGE` = 3 |
| 精英「投矛」 | 对最前排植物 **100 伤害** | **70 伤害**，且南瓜优先承伤 | `TF_ELITE_SPEAR_DAMAGE` = 70 |
| 僵王 P1 砸击 | 2×2 直接 `Die()` **+** 半径 60 秒杀（双重） | 半径 110px，**1500 伤害** | `TF_BOSS_SLAM_DAMAGE` = 1500 |
| 僵王 P3 咆哮 | 整列直接 `Die()` | 整列 **2000 伤害** | `TF_BOSS_ULTIMATE_DAMAGE` = 2000 |
| 僵王 P2 地形转水 | 非睡莲植物**无声淹死** | 有南瓜 → **南瓜替它沉**，植物保住 | — |

> **刻意保留的两个瞬秒**（用户明确要求不动）：小丑僵尸爆炸（半径 190px）
> 与气球僵尸被击落后的爆炸 —— 这两种僵尸本身脆皮，保留「一换多」的爆发是它们的角色定位。

## 3.17 「场外黑区」：为什么辣椒头僵尸能凭空炸掉一整行

实测反馈：魅惑僵尸会往场外走，在**第 10 列**（草坪右边缘之外）和敌人互啃；
敌人被啃住后**走不进场内**，植物又打不到它；结果一旦被啃的是辣椒头僵尸，
它就在**场外**把一整行植物清掉 —— 玩家看不见、够不着、完全无法反制。

### 3.17.1 三个事实（读代码确认）

| # | 事实 | 依据 |
|---|---|---|
| 1 | 草坪网格右边缘 = **x 760** | `GridToPixelX(col) = col × 80 + LAWN_XMIN(40)`，`MAX_GRID_SIZE_X = 9` → 40 + 720 = 760 |
| 2 | 僵尸**全部**在场外出生 | `Zombie::ZombieInitialize`：`mPosX = 780 + Rand(...)` |
| 3 | 辣椒头僵尸的引爆是**帧计时**，与血量无关 | `Zombie::Update`：`if (mPhaseCounter > 0 && !IsImmobilizied()) mPhaseCounter--;` —— **走路或原地啃都照走**；`UpdateZombieJalapenoHead` 在 `mPhaseCounter == 0` 时把该行所有植物 `Die()` |

把 3 串起来就是那个"没法反制"的现象：它出生在场外 → 被魅惑僵尸挡在场外啃住 →
计时照样走完 → **在场外引爆一整行**。

> 顺带修正一个直觉误区：它**不是**「被啃到一定血量才炸」，而是纯粹的计时。
> 血量 500，打早了直接死（不会炸）；打晚了就炸。所以「500 血、约 7～13 秒」本来是设计好的反制窗口，
> 只是因为场外那次引爆，这个窗口对玩家来说根本不存在。

### 3.17.2 修复：把「场外」定义成不允许发生任何战斗/爆炸的区域

新增分界线常量 `TF_FIELD_RIGHT_X = 760`（草坪右边缘），规则两条：

**① 辣椒头僵尸场外不引爆** —— `Zombie::UpdateZombieJalapenoHead` 开头：

```cpp
if (ThirtyFlagsMode() && mPosX > TF_FIELD_RIGHT_X && mPhaseCounter < TF_JALAPENO_MIN_FUSE)
{
    mPhaseCounter = TF_JALAPENO_MIN_FUSE;   // 场外把计时顶回到 700 帧
    return;
}
```

等价于「计时只在场内推进」。因为 `TF_JALAPENO_MIN_FUSE`(700) 大于任何僵尸在场外停留的时间，
它**一定**是在走进场地之后、且还剩完整接近窗口时才引爆 —— 玩家看得见、也打得到。

> 这个下限只会**延长**引爆时间，不会缩短：原始计时是「按速度折算的 275～450px 步行帧数」，
> 短的那些（≈550 帧）会被顶到 700 帧（对玩家更宽松），长的那些（≈1300 帧）不受影响。

**② 魅惑僵尸不在场外开战** —— `Zombie::FindZombieTarget` 里忽略场外目标：

```cpp
if (ThirtyFlagsMode() && aZombie->mPosX > TF_FIELD_RIGHT_X)
    continue;
```

这样敌人会正常走进场地，战斗只发生在植物能参与的位置；
同时消除了「敌人被永久卡在场外」导致的**本旗无法结束**的潜在死锁。

### 3.17.3 日志

```
[TFPlant] jalapeno ignition DEFERRED (offboard x=812)
```

只在这一下「真的差点引爆」时打印，可以直接验证修复是否生效。


## 3.18 实测四问：迷雾失效 / 水路叠种 / 18 旗崩溃 / 掉帧

### 3.18.1 迷雾没生效：`StageHasFog()` 只认雾天场景

`ThirtyFlagsSetupBoard` 确实把雾写进了 `mGridCelFog`（右侧 `mFogCols` 列 = 255），
但**没有任何人画它**：

```cpp
bool Board::StageHasFog()
{
    return !IsStormyNightLevel() && mGameMode != ..._INVISIGHOUL
        && mBackground == BackgroundType::BACKGROUND_4_FOG;   // ← 只有雾天场景才算有雾
}
```

`DrawFog` 的渲染项（`RENDER_ITEM_FOG`）只在 `StageHasFog()` 为真时才注册，
所以白天草坪上这团雾永远是「写进了数据但没人画」；路灯花也因为「本关没雾」而不可用。

**修复**：让三十旗在「本旗配置了迷雾列」时也算有雾；

```cpp
(mBackground == BACKGROUND_4_FOG || (ThirtyFlagsMode() && gThirtyFlags.mFogCols > 0))
```

同时 `Board::UpdateFog()` 在三十旗下直接 `return` —— 原版那套是
「`LeftFogColumn()` 起的逐帧淡入 + 植物周围自动开雾」，而非冒险模式下
`LeftFogColumn()` 固定返回 **5**，会把三十旗的 3 列雾变成 4 列；三十旗的雾应当由
`SetupBoard` 按本旗配置直接写入（持续迷雾）。

### 3.18.2 水路不能叠种：睡莲被算进了「同格 3 株」

`Board::CanPlantAt` 的叠种判定数「同格植物数」，但把**睡莲/花盆（底座层）**也算进去了：

水路上「睡莲 + 南瓜 + 植物」= 已经 3 株 → 永远叠不了第 4 株。

**修复**：计数时跳过 `SEED_LILYPAD` / `SEED_FLOWERPOT`（它们是底座层，不是叠种的三株之一）。

### 3.18.3 第 18 旗崩溃：`ReanimationGet(0)` 空指针

崩溃日志（`Release\pvzdebug.log`）给出了完整链路：

```
ASSERT DataArray.h(232)  condition: aItem != nullptr
                         detail: Failed: DataArrayGet(0x0) for reanims
!!! UNHANDLED EXCEPTION 0xC0000005 (ACCESS VIOLATION)
!!! read at address 00000004      ← 空指针 + 偏移
      survivalStage=17            ← 也就是第 18 旗（旗帜僵尸出场那一旗）
```

`REANIMATIONID_NULL == 0` 是「没有特殊头部动画」的哨兵值。而**三十旗让旗帜僵尸直接
调用 `UpdateZombieGatlingHead()`**（原注释：「旗帜僵尸 = 机枪僵尸的 id」），
那个函数会对 `mSpecialHeadReanimID` 调 `PlayReanim("anim_shooting")` / `("anim_head_idle")`：

* 这两条是**机枪豌豆头**的动画；旗帜僵尸的"特殊头部"其实是**旗子**（`REANIM_FLAG`），没有这两条动画；
* 更致命的是这个 id **会被清空**（`DropFlag()` 在丢掉旗子时 `RemoveReanimation` 了它，
  却没有把 id 置回 `REANIMATIONID_NULL`；`Zombie::UpdateZombieSquashHead` 那条路径则显式置 0），
  之后任何 `ReanimationGet(它)` 就会 `DataArrayGet(0)` → 断言 → 空指针访问。

**修复（两条）**：

1. `DropFlag()` 释放旗子后把 `mSpecialHeadReanimID` 置回 `REANIMATIONID_NULL`（消除失效 id）；
2. 旗帜僵尸的射击**不再借用机枪头的 AI**：射击节奏改由
   `ThirtyFlagsZombieUpdate` 自己实现（与机枪头同节奏：150 帧 4 发、`PROJECTILE_ZOMBIE_PEA`
   朝左飞），并把一个**真的机枪豌豆头**作为纯视觉挂在 `anim_head1` 轨道上
   （`REANIM_GATLINGPEA` + `anim_head_idle`），**不占用 `mSpecialHeadReanimID`**。

> 这样"头是机枪头、旗子是旗子"各管各的：既满足「战争之王长机枪头」的设计，
> 又不会再出现 `ReanimationGet(0)`。
>
> 「战争之王」的护甲按用户口径重调（`TF_FLAG_ARMOR_*`）：
> **高坚果护甲 = 8000（本体血量）**、**橄榄球头盔 = 1400**（= 原版 `ZOMBIE_FOOTBALL` 的数值，
> 原版就是 1400，不是记忆里的 1700~3700）。
> 另注：现存实现还挂了一层**铁门盾（1100）**，那是更早的「三件套」设计，
> 本次未动 —— 若要严格按「两件防具」，把 `mShieldType` 那三行删掉即可。

### 3.18.4 掉帧：瓶颈在「每个投射物都拖着骨骼动画」

**先排除一个猜测**：不是实体池爆上限。崩溃现场 `projectiles=245/1024`、`plants=94/1024`、
`zombies=49/1024`，都远没满；日志里也**没有任何** `DataArray FULL` 记录。

真正的量级差异在于 **Reanimation（骨骼动画）**：它是这个引擎里最贵的每帧对象
（逐帧解算骨骼轨道 + 变换后逐帧绘制 cel）。而：

| 来源 | 是否创建骨骼动画 |
|---|---|
| 每株植物 | 是（本体 + 头部/挂件） |
| 每个僵尸 | 是（本体 + 头 + 头盔/护盾/挂件） |
| **每个火球投射物** | **是** —— `AttachFirePeaReanim()` 会给火球挂一个 `REANIM_FIRE_PEA` |
| 火炬树桩「点燃」 | 每颗经过的豌豆被 `ConvertToPea` 成火球 → 又是一条 |

所以「叠种机枪 + 叠种冰瓜 + 火炬 roll」这条链的代价不是「植物多了几株」，
而是**投射物数量被成倍放大**（机枪 4 发/轮 × 叠种株数 × 火炬把每颗豌豆变成带骨骼动画的火球），
而每颗带动画的弹都要占一条骨骼动画的更新与绘制。**这与你「物品创建太多」的直觉是同一个方向**，
只是瓶颈在骨骼动画而不是实体池。

另外两条会被这次放大放大的**纯浪费**：

* `ProjectileInitialize` 的 `PROJECTILE_FIREBALL` 分支只有一句 `TOD_ASSERT()`
  —— 没有做任何初始化。实测日志里 `Projectile.cpp(101)` 被打了 **1600+ 次**，
  每打一次就是一次磁盘写（`channels=FFFFFFFF / level=3`，日志全开）。
* 精英「投矛」的矛原来没设运动模式，走默认「向右 3.33/frame」——
  从僵尸身上朝僵尸堆方向飞、几十帧就出界，玩家根本看不到（实测反馈"没见过这根矛"）。
  已改为 `MOTION_BACKWARDS`（朝它刚刺中的植物方向飞），既可见也不做碰撞。

**建议的下一步**（按性价比排序）：

1. 日常游玩用 **`PlantsVsZombies_Play.exe`**（`TF_PLAYER_BUILD` + `PVZ_DEBUG_ENABLED=0`），
   调试版开着全量日志与断言，代价不小；
2. 若要继续压投射物数量，从「火炬把每颗豌豆变火球」入手（比如给转换加节流），
   那是本作投射物数量最大的乘数；
3. 需要精确定位时，可以在 `ThirtyFlagsBoardUpdate` 首尾各取一次
   `GetTickCount()`，把最慢的帧连同当时的实体数写进 flow log —— 有了数据再决定动哪里。

`tools/tf_mower_auto.ps1` 是**自持进程**的回归脚本：它自己在同一个进程里启动游戏 → 等窗口 / 加载完成 →

> 1. **必须让「脚本 → 游戏」在同一个工具调用里存活到底**。游戏进程一旦和启动它的 shell 脱钩，
>    就会被环境回收 —— 表现为脚本还在跑、游戏已经没了。所以脚本要 `Start-Process -PassThru` 并全程持有 `$p`。
> 2. **`.ps1` 文件必须带 UTF-8 BOM**。PowerShell 5.1 对无 BOM 文件按 GBK 解码，中文注释会把紧跟的
>    引号 / 花括号吞掉，报「表达式或语句中包含意外的标记 `}`」这种莫名其妙的位置错误。
> 3. **不要用整屏截图**验证（`CopyFromScreen`）：机器被占用时游戏窗口可能被压在别的窗口下面。
>    用 `PrintWindow(hwnd, dc, 2)` 抓窗口自身内容，与遮挡、焦点都无关。

> 另外：本机是**锁定 / 有别的窗口占用**时，游戏有较大概率卡在「建完窗口但没画第一帧」的状态

## 6. 已知风险与后续建议

| 风险 | 说明 | 建议 |
|---|---|---|
| 水路行的**视觉**表现 | 采用「整行 `PLANTROW_POOL` + 仅右侧 N 列为 `GRIDSQUARE_POOL`」实现。水面来自泳池背景图，因此**水行左侧的陆地区段在画面上仍显示为水**（逻辑上不可种水生植物、可种陆地植物） | 若要视觉与逻辑完全一致，需要从 `IMAGE_POOL_BASE` / `ALMANAC_GROUNDPOOL` 剪出单格水面与陆地贴图，在 `Board::DrawBackdrop` 里按格重绘 |
| 精英词条的字段借用 | 依赖「这些 `mBoss*` 字段只在 `ZOMBIE_BOSS` 分支被读写」这一事实（已全文件核对） | 若后续有人为非 Boss 僵尸使用这些字段，需改为在 `Zombie` 上新增独立成员（并注意 `SyncBoard` 的存档兼容） |
| 魔数 `bit 8` 作为「植物来源伤害」标记 | 与 `DamageFlags` 现有位不冲突，但属于隐式约定 | 若要长期维护，建议在 `DamageFlags` 里正式加一项 `DAMAGE_FROM_PLANT` |
| 「共生·水路」补空卡槽的实现 | 通过直接改 `mSeedBank->mNumPackets` 实现，种多株睡莲会持续加槽（受 `TF_SEED_SLOTS_MAX` 上限约束） | 更干净的做法是在 `Board::GetNumSeedsInBank()` 里按「已种睡莲数」计算 |
| 6 波/旗 与 180 波总数 | `MAX_ZOMBIE_WAVES = 100` 是 `mZombiesInWave` 的行数上限。当前每旗只预生成 6 波，未触碰上限；但如果把 `TF_WAVES_PER_FLAG` 调大或取消「每旗重建波次表」，需要同步把 `MAX_ZOMBIE_WAVES` 提到 ≥180 | 调整 `TF_WAVES_PER_FLAG` 时留意此约束 |
| 存档兼容 | **直接复用原版 `SaveGame` 通路**（详见 §3.10）。`Board` 状态（格子 / 植物 / 阳光 / 小推车 / 波次表 / `mSurvivalStage`）由 `SyncBoard` 整体写盘；只有肉鸽层（强化层数 / 词条 / 整备期）因为**不能给 `Board` 加成员**（`SyncBoard` 按 `sizeof(Board)` 整块写）而单独落在 `<存档>.tf` 附加文件 | 往 `ThirtyFlags` 加新的跨旗状态时，记得同步加到 `ThirtyFlagsOnSaveGame` / `ThirtyFlagsOnLoadGame` 的读写列表，否则重进游戏会丢失 |
| 平衡未经实机校准 | 策划案第 9 章的公式只落地了成长曲线；`TF_BALANCE_KNOB` 目前**未被引用** | 实机跑通后按「熟练玩家通关率 30%–50%」反推校准 `TF_HP_GROWTH_PER_FLAG` 与 `mZombiePoints` |
| **`properties\LawnStrings.txt` 必须是 UTF-16 LE + BOM** | ⚠️ 已踩过的坑：`TodStringListReadFile` 用 `p_ftell(pFile) / sizeof(SexyChar)` 得到字符数后**按 `SexyChar`（=wchar_t，2 字节）整体读取**，即该文件被当作 UTF-16 直接映射。改成 UTF-8（哪怕带 BOM）会让解析全乱，游戏启动即弹 `Failed to load string list file 'Properties\LawnStrings.txt'`，**画面全黑但进程存活**。原始文件头为 `FF FE` | 只增不改时，用 `Encoding.Unicode` 读写（会写 BOM）；不要用 `Encoding.UTF8`。新增键值对即可，无需重打包 `main.pak`（磁盘文件优先） |
| 判断启动是否成功 | ⚠️ 已踩过的坑：只看「进程存活 / 窗口被创建」会误判成功——`SexyAppBase::Start()` 在 `LawnApp::Init()` 之前就已建好窗口，失败时窗口照样存在，只是全黑 | 必须同时确认「无 `#32770` Error 对话框」且「标题画面已渲染」（截图或 `PrintWindow`） |
